# 资产池准入材料整理

> 本技能为尽调材料组织类技能的伞(umbrella),已吸收以下技能(2026-08 合并):
> `evidence-package-organization`、`fund-dd-organization`、`fund-due-diligence-material-org`、`due-diligence-evidence-packaging`。
> 各技能的完整原文见 `references/absorbed-*.md`,独特细节(通用解压流程、拼音目录名坑、python-docx 模板复用、git 纪律)已并入正文相应小节。

## 概述

信托公司FOF业务中，基金管理人申请调入资产池（基础池/备选池/核心池）需要按逐条条件提交佐证材料。本 skill 覆盖从原始尽调材料到最终编号文件的全流程整理。

适用场景：
- 粤财信托等信托公司资产池准入申请
- 私募基金管理人尽调材料按条件分拣
- 填写《资产池调整申请表》的配套材料准备

## 池类型与条件体系

三类资产池的条件性质不同，**每类独立编号（从 01 开始）**：

| 池类型 | 条件性质 | 编号 | 示例 |
|--------|---------|------|------|
| **基础池** | 硬性资格门槛（备案、实缴、成立时间、合规、材料齐全） | 独立 01-0N | 01 协会备案、02 实缴资本 ≥ 1000 万 |
| **备选池** | 能力类标准（团队、业绩、风控） | 独立 01-0N | 01 投研占比 ≥ 50%、02 业绩正收益 |
| **核心池** | 流程性要求（现场尽调、评分、≥75 分转入） | 独立 01-0N | 01 现场尽调、02 综合评分表、03 评分 ≥ 75 |

**关键：每类池独立编号，从 01 开始。** 基础池的 01 和备选池的 01 是不同的条件。conditions.md 中三类池分开记录，互不引用。

**核心池证据来源：** 核心池条件的证据文件（1–、2–、3–）从目标管理人的参考文献 `references/<管理人>/` 中选取对应的尽调材料（尽调问卷、绩效归因报告、备案截图等）。核心池证据不来自其他管理人的已填写模板（辰元的尽调记录、评分表、尽职调查报告等），也不来自评审流程（现场尽调尚未发生）。按\"存在就放，不存在就不放\"原则处理。

## 工作流

### Step 0：以现有结构为模式参考

在创建新池目录前，先打开一个已有的同类型池文件夹看结构。用 `ls docs/jul-*-<pool-type>/` 或 `execute_code` 列出文件，确认模式后再动手。不要凭记忆猜测结构。

### Step 0.1：创建目录与 git 绑定

```
docs/jul-<DD>-<manager>-<pool-type>/
```

池类型英文：basic-pool / alternative-pool / core-pool

**Git 纪律（第一优先级）：每完成一个操作步骤（创建/复制/编辑/替换/删除），立即：**
```bash
git add <具体文件路径>   # 精确指定，禁止 git add . 或 git add -A
git commit -m "feat|fix|chore: <英文祈使语气描述，≤72字>"
git push
```
**用户对 git 的偏好：** 明确要求"不是下班前git，而是每步操作完都git"。每次产生文件变更后立即走完 add→commit→push 全流程（即使这意味着一连串小提交），不要等一天结束时才批量提交。同事也在同一仓库工作，不及时推送会造成冲突。

**提交信息格式（详见 AGENTS.md 第十一节）：**
- 严格使用 prefix: `feat` `fix` `docs` `refactor` `chore` `reorg` `cleanup`
- subject 英文祈使语气，首字母小写，≤ 72 字符
- 涉及编号文件时标注编号范围（如 `conditions 01-03`）
- 禁止纯 `update`/`fix`/`add` 等无信息量的 commit

**留痕要求（Traceability）：**
1. 同一管理人、同一池的材料变更合并在一个 commit 内；不同管理人、不同池分多次 commit
2. commit 只包含直接相关文件，不混入 .gitignore 等无关改动
3. 二进制文件（xlsx/docx/pdf）在描述中标注具体文件名
4. 一次 commit ≤ ~10 文件，超则拆分
5. 下班前检查：`git status` 干净；`git log --oneline origin/main..HEAD` 无未推送 commit

### Step 0.5：条件来源文档与 0– 文件规则

如有制度文件/指引作为条件依据，可以放入工作目录，但**不要标记为 0–**。

**0– 文件的唯一身份：** `0–` 文件永远是**资产池调整申请表**（`0–广东粤财信托有限公司资产池调整申请表+<管理人>+调入<池类型>.docx`），规则原文、制度文件、尽调记录模板等都不是 0–。当有多个非申请表的源文件需要保留时（如规则 JPEG、原始模板），按实际情况编号或只在 conditions.md 中引用，不得抢占 0– 位置。

### Step 1：了解条件列表

获取该池类型的完整条件文本，每个条件对应一个独立编号：
- **基础池**：硬性门槛类条件（备案、实缴资本、成立时间≥1年、合规、材料齐全）
- **备选池**：能力类条件（投研团队、业绩表现、风控合规）
- **核心池**：流程类条件（现场尽调、综合评分表、评分≥75分）

### Step 1.5：多池分发模式

同一份源文件可能需要同时放入多个池目录（basic/alternative/core），每个池独立编号：

```
源文件：尽调问卷.docx

分发到：
  basic/0–尽调问卷.docx        (basic 的 0 号)
  alternative/0–尽调问卷.docx   (alternative 的 0 号)
  core/0–尽调问卷.docx          (core 的 0 号)

源文件：制度文件/ (10 份 PDF)

→ alternative/1–制度文件/...
```

**规则：**
- 每个池独立编号，从 0 开始（0 = 申请表）
- 同一文件在不同池中编号不同
- 用户一次指定一个源→目标映射，不要批量猜测
- 每个 cp 后立即 git commit + push

### Step 2：定位原始文档

从 references/ 下的原始目录（due-diligence-materials, supplementary-due-diligence, chenyuan 等）中，按条件需求提取相关文件。

常用映射：
| 条件 | 原始来源 |
|------|---------|
| 协会备案/执照 | 01-company-profiles/manager-info-disclosure, business-license |
| 实缴资本 | 01-company-profiles/financial-report-filing 或 03-audit-reports |
| 产品/业绩 | 04-fund-contracts, 05-fund-fact-sheets, 06-valuation-reports, 08-performance-attribution |
| 合规声明 | 01-company-profiles/due-diligence-questionnaire |
| 团队 | due-diligence-questionnaire（团队章节）+ manager-info-disclosure |
| 风控制度 | 02-internal-policies/ |
| 绩效（第三方） | 08-performance-attribution（中信证券第三方平台报告） |

### Step 2.5：外部信用核查

基础池条件 04（无违法违规/诉讼）和备选池条件 03（风控合规）需要从以下外部公开平台查询管理人的信用/执行/行政处罚记录。查询结果截图或导出 PDF 可作为合规证据。

**标准查询清单：**

| 平台 | URL | 查询内容 |
|------|-----|---------|
| 中国执行信息公开网 | zxgk.court.gov.cn | 被执行人信息、失信被执行人名单（查管理人全称） |
| 国家企业信用信息公示系统 | gsxt.gov.cn | 行政处罚、经营异常、严重违法失信名单、年报信息 |
| 证券期货市场失信记录查询平台 | neris.csrc.gov.cn/shixinchaxun/ | 证券期货市场失信记录（需姓名+证件号） |
| Wind 3.1M | Wind 桌面终端功能 | 诉讼/失信/行政处罚一站式查询（仅限有 Wind 终端的场景） |

**查询步骤：**
1. 用浏览器打开每个平台
2. 输入管理人全称搜索（中国执行信息公开网和失信记录平台需输入完整名称）
3. 若无记录 → 截图或网页另存为 PDF 作为"无违规记录"证据
4. 若有记录 → 截图记录详情，在 conditions.md 中标注

**注意事项：**
- 国家企业信用信息公示系统有时需验证码 / 登录，若无法直接访问则记录为"需人工核查"
- 证券期货市场失信记录平台需要姓名+身份证号/证件号。法定代表人身份证号可从 **公司章程（articles of association）** 或尽调问卷中提取。搜索 `references/<管理人>/` 下的 `articles-of-association.md` 或 `complete-articles-of-association.md`，关键词 `身份证号码`。
- Wind 3.1M 是桌面终端功能，非网页，无法通过浏览器打开
- 查询结果可作为条件 04 的辅证材料（编号 `4–第三方查询结果汇总.pdf`）

**截图合并为 PDF：**
多个第三方平台的查询截图可合并为一个 PDF 文件，避免目录被碎片化的小图片塞满。

```python
from PIL import Image

files = ['screenshot1.png', 'screenshot2.png', ...]
images = [Image.open(f).convert('RGB') for f in files]
images[0].save('4–第三方查询结果汇总.pdf', save_all=True, append_images=images[1:])
```

合并后删除单个 PNG，只保留 PDF。
编号规则：`N–第三方查询结果汇总.pdf`（N 对应条件编号）。

**渠道说明：**
- 云浏览器（browser_navigate）可在后台直接打开全部三个平台页面，但实名认证/验证码页面需要人工操作
- 当需要用户亲自操作时，用 Computer Use MCP 打开 macOS 本地 Safari：`get_app_state('Safari')` → 点击地址栏 → 输入 URL → Return 导航。告诉用户页面已打开让他们亲自搜索
- 截图后及时 commit+push（每张或多张一批，不等下班）

最终目录下的所有文件必须遵循：

```
<条件编号>-<子项编号>-<中文描述性文件名>.<ext>
```

**规则：**
- 编号与申请表"对应申请辅证材料明细"列的编号完全一致
- 编号与中文名之间用 **en dash (–, U+2013)** 连接，不是空格
- 中文名必须是**完整清晰的描述**，如 "营业执照副本"、"2025年第四季度财务报表"
- 不允许出现 .md 格式的佐证材料——证据文件必须是 PDF、DOCX 或 DOC
- 所有文件平铺在同一个目录下，**不允许嵌套子目录**
- 文件名不含拼音缩写、英文前缀
- 申请表（0–）同样按此规范：`0–广东粤财信托有限公司资产池调整申请表+<管理人全称>+调入<池类型>.docx`

### Step 4：文件格式要求

- 从 references/ 复制时：
  - 如果原始文件是 .md，且申请表引用它作为证据 → 转为 .docx 保存
  - 如果原始文件有 .pdf 和 .md 两个版本 → 只保留 .pdf，.md 删除
  - 纯文本参考文件（conditions.md 等汇总文件）可以保留 .md
  - 用户直接提供的 .doc 文件（如基金经理介绍.doc）→ 保留原格式，删除同名的 .md

### Step 5：填入申请表——模板替换规则

**模板适用范围 ⚠：申请表（0–）是唯一允许从其他管理人复制模板的文件。**

**关于证据文件（1–、2–、3–等）：**
- ✅ 允许：从 `references/<目标管理人>/` 复制目标管理人自己的原始尽调材料，按条件编号命名
- ❌ 禁止：把其他管理人（如辰元）已填好的尽调记录、评分表、尽职调查报告直接复制到新管理人的目录中当证据。这些文件包含其他管理人的具体数据（团队介绍、策略说明、业绩数据），不是可复用的空白模板。
- ❌ 禁止：根据记忆或已有资料自行编造团队介绍、策略说明、业绩数据
- 如果目标管理人没有某个核心池条件的证据文件（如尚未产生现场尽调报告），则**不要创建该文件**，只保留 conditions.md 和 0- 申请表。对应的 1-、2-、3- 目录留空，等用户提供或后续流程生成。

**申请表内容替换规则（严格执行）：**
- ✅ **只改以下字段：** 管理人名称、申请池类型（基础池/备选池/核心池）、调整方向（调入/调出）、申请日期、对应辅证材料引用编号
- ❌ **禁止自行填充：** 不得根据记忆中查阅过的尽调材料自行编造团队介绍、策略说明、业绩数据。这些内容必须等用户提供或从 actual reference 文件中提取
- ✅ **标准条件文本：** 保留申请表原模板中的入池标准文字不动（如"投研及技术人员占比≥50%"是粤财的固定模板文字）
- 从其他管理人复制模板后，先改名字再填证据引用，防止遗漏

申请表文件名格式：
`0–广东粤财信托有限公司资产池调整申请表+<管理人全称>+调入<池类型>.docx`

### Step 6：清理

确认申请表无误后，删除：
- 所有原始 .md 文件（已转换为 .docx 的）
- 所有在中途创建的旧目录/子目录
- 申请表引用列表之外的所有冗余文件

最终目录应只剩：编号文件 + conditions.md + 申请表（0–）+ 可能有的来源文档（0–）

### Step 7：创建评分表（核心池）

核心池条件 02 要求《私募管理人综合评分表》。评分表从同类管理人模板复制，但**所有数据必须从目标管理人 references/ 中精准提取**，不得复制其他管理人的评分意见或编造数据。

评分表的完整维度和数据来源参见 `references/scoring-table-dimensions.md`。

**⚠ 模板行数确认：** 辰元模板有 32 个细分评分子项，但用户手上的实际模板可能已简化为 **9 行**：
- 5 个构面（公司生存发展能力/投资研究能力/风险管理能力/服务评价/业绩因子）各一行
- 4 个补充项（服务评价细项、产品特征因子等）

**两种填写方式：**
- **32 行版（辰元模板）：** 逐个子项填入评价意见和分数，计算加权总分
- **9 行版（简化模板）：** 直接提供每个构面的加权得分和总分

**模板选择：复制 .xlsx，不创建 .xls**
- 优先复制其他管理人已有的 .xlsx 模板（如辰元模板），而不是创建新的 .xls 文件
- .xlsx 由 openpyxl 处理，保留了合并单元格、列宽、公式和格式；老式 .xls（xlrd/xlwt）容易丢失合并单元格信息

**⚠ 核心规则：只修改 M 列（评价人意见）和 N 列（评价人打分），不动其他任何列**
- 模板的 A-K 列（序号、构面、权重、评分标准等）是标准评审文本，已经填好，不要写入任何数据
- **常见错误：往 C 列（权重比例位置）写入策略类型描述文字**（如"以股票为主要投资标的的私募基金"），这些文字来自 Sheet 1（评分说明），不属于评分表
- 所有不必要的文字（策略定义、策略细分等）放入评分表会被 boss 判定为"莫名其妙的东西"
- 只在评价人意见列（M）和打分列（N）写入内容

**评分构面与权重参考：**
| 构面 | 权重范围 | 数据来源 |
|------|---------|---------|
| 公司生存发展能力 | 10%-20% | 尽调问卷（公司概况/财务/股权/合规） |
| 投资研究能力 | 10%-20% | 尽调问卷（团队/策略/投委会/交易） |
| 风险管理能力 | 10%-20% | 尽调问卷（风控）+ 风控制度 PDF |
| 服务评价 | 10%-14% | 沟通配合情况 + 材料完整性 |
| 特征因子、业绩因子（定量） | 30%-50% | 绩效归因报告（夏普/回撤/超额收益） |

**流程：**
1. 从其他管理人的核心池模板中找到评分表 .xlsx，复制为 `3–私募管理人综合评分表——<目标管理人>2026年<月>月.xlsx`（注意后缀是 .xlsx，不是 .xls）
2. 使用 `openpyxl` 打开，只修改 M 列（列 13，评价人意见）和 N 列（列 14，评价人打分）：
   - M 列：写出基于实际数据的评价判断（简洁、有依据，参考模板"1.2.3均符合"式写法）
   - N 列：根据评分规则赋分
3. **不要修改 M/N 以外的任何列**——不要写序号、构面、权重、策略类型到错误的单元格
4. 每个评分项的数据必须有 reference source file 可验证：
   - 基本资料 → 尽调问卷 + AMAC 备案
   - 业绩因子 → 绩效归因报告（第三方平台具体数据：成立以来年化、近3月/6月/1年收益、最大回撤、夏普）
   - 团队 → 尽调问卷团队表 + 经理简介
   - 风控 → 风控制度 + 尽调问卷合规声明
5. **完成后清理：** 评分表已包含全部量化数据，之前用作数据源的绩效归因报告 PDF 可删除（保留评分表即可）

**⚠ 不要用 openpyxl 从零创建评分表**  
- 模板有 33 个合并单元格，从零创建容易触发 `'MergedCell' object attribute 'value' is read-only` 错误  
- 始终复制已有模板后修改数据单元格，不要重建合并逻辑  

**⚠ 模板含图片时，openpyxl 的 save() 会损坏图片锚点**  
- 如果评分表模板 .xlsx 中包含图片/图表（如图章、logo），直接 `openpyxl.load_workbook` → `modify cells` → `wb.save()` 会损坏图片的 XML 锚点引用，导致打开时报 `Cannot read properties of undefined (reading 'anchors')`  
- **解决方案：** 完全绕过 openpyxl，直接通过 zipfile 操作底层 XML：  
  1. 复制模板后，用 `zipfile.ZipFile` 读取全部文件到 dict  
  2. 删除 `xl/drawings/`、`xl/media/` 下的图片/绘图文件  
  3. 同步清理 `[Content_Types].xml` 中的 `<Override>` 和 `<Default>` 引用，清理 `xl/worksheets/_rels/sheet2.xml.rels` 和 `xl/worksheets/sheet2.xml` 中的 `<drawing>` 引用  
  4. 修改 `xl/sharedStrings.xml`：在 `</sst>` 前追加新的 `<si>` 元素（每个 M 列评价用共享字符串）  
  5. 修改 `xl/worksheets/sheet2.xml`：更新 M 列 `<c r="M{row}" t="s"><v>{index}</v></c>` 的 index 指向新追加的共享字符串索引；更新 N 列的 `<v>{value}</v>` 数值  
  6. 重新 ZIP 打包回 .xlsx  
- 为什么不用 openpyxl：模板的 M 列使用**共享字符串**（shared strings），不是内联字符串（inline strings）。openpyxl 修改共享字符串表时会重写整个 drawing 的 XML 引用，而 zipfile 方式只动文本内容，不动二进制图片和绘图结构。

### Step 8：打包发送

如需发送给同事，将所有文件（0–到N-N）打包到 tmp/ 下的 zip：

**核心池编号规则：** 核心池的 1- 文件（现场尽调记录）在初次材料准备阶段通常为空，不是立即生成的。**不要自行编造或从其他管理人复制**。用户会明确定义各条件对应的文件编号。
```bash
zip -j /path/to/tmp/<描述>.zip <编号文件列表>
```

## 常见陷阱

1. **拼音顺序搞反** — "多和美"是 duohemei，不是 heduomei。中文公司名拼音不要想当然，看一眼原文确认。
2. **文件名中的公司名必须先验文件内容** — 修改文件名中的管理人名称时，**必须先用 python-docx / fitz 打开文件，从表格或正文中确认完整公司名称**，再改文件名。不要凭目录名称、文件名上下文或记忆中的简称来推断。特别是\"臻远\"这类公司，文档内的全称可能是\"广东臻远私募基金管理有限公司\"而非\"深圳市臻远投资顾问有限公司\"。用户对此类错误极严厉。规则：**先读文件内容，再改文件名，顺序不可逆。**
2. **子目录嵌套** — 不要用 03-products/ 这种中间目录。所有编号文件直接放根目录。
3. **佐证材料用 .md** — 申请表里的证据不接受 markdown，必须 PDF、DOCX 或 DOC。
4. **文件名混用英文** — 不要 "01-amac-filing.pdf"，要 "1-1–私募基金管理人公示信息.pdf"。
5. **编号不匹配** — 文件名编号必须和申请表"对应申请辅证材料明细"列完全一致。
6. **条件分组混淆** — 三类池条件在 conditions.md 中分开记录，编号不跨池延续。
7. **核心池当资格条件做** — 核心池条件是流程性要求（现场尽调→评分≥75），不是管理人的硬性资格，证据由评审流程生成。
8. **申请表模板里忘了改管理人名字** — 从其他管理人复制模板后，先改名字再填证据，防止遗漏。
9. **把其他管理人的已填写模板当证据用** — ⚠ 核心池及备选池的证据文件必须来自目标管理人的 reference 材料（`references/<管理人>/`）。严禁把其他管理人（如辰元）已填好的尽调记录、评分表、尽职调查报告直接复制到新管理人的目录中充当证据。这些文件包含其他管理人的具体数据（团队、策略、业绩），不是可复用的空白模板。正确做法：只从 references/ 中复制目标管理人自己的原始尽调材料（尽调问卷、审计报告、绩效报告等），按条件编号命名。申请表（0–）是唯一可以从其他管理人复制模板并替换公司名的文件。
10. **用户说"继续念"时自行编造条件** — 当用户说"继续念"或"我给你念条件"时，意味着用户将口述条件内容。**不要根据记忆或已有资料自行推导/编造条件文本或证据内容**。等待用户提供确切内容后再记录。特别是核心池条件（现场尽调、评分表、门槛分）——用户有原始制度文件，不要凭之前的文档自行编写。
11. **备选池忘记重新编号** — 粤财标准中备选池条件原始编号为 06-08，但工作目录、文件名、conditions.md 都必须重新编号为 01-03（每个池独立编号）。用户会明确发出"把678改成123"的指令。不照做会导致文件名与条件不匹配。
13. **没有就没有，不准复制** — 如果目标管理人 references/ 下不存在某个条件的对应证据文件（如尚未产生现场尽调报告、尚未填写评分表），则**不要创建该文件**。严禁把其他管理人（辰元）已填好的模板复制过来充数（"不准复制，没有就没有"）。只保留 conditions.md 和 0- 申请表，对应的 1-、2-、3- 留空等用户提供。
14. **检查已有文件夹结构再动手** — 动手前先 `ls docs/jul-*-<pool-type>/` 看看同类池的真实文件列表。用户会纠正"完全搞错了，你再看看xxx的文件夹结构"。不要凭记忆猜测结构。
15. **核心池 0– 文件是申请表，不是其他文档** — 核心池的 `0–` 文件必须是申请表。不要把条件来源文档（如规则 JPEG）或尽调记录模板标记为 0–。用户明确说"这个是唯一0-文件"。
16. **评分表数据必须精准从 references 提取** — 每一个评分项的评价意见和得分必须从 references/ 中的实际文件提取（尽调问卷、绩效归因报告、审计报告等）。不得编造数据或复制其他管理人的评价。"精准查找精准赋分"是用户明确要求。
17. **`conditions.md` 先读再动手** — 进入新池的工作目录后，第一条操作是 `read_file conditions.md`。条件到证据的映射已写在里面，不需要自己重新推导。

18. **评分表填完后记得清理源数据文件** — 完成评分表填充后，之前作为数据来源的绩效归因报告 PDF 可以删除。评分表已经包含了所有需要的量化数据，保留单独 PDF 是冗余。

19. **评分表模板行数可能有差异** — 辰元的评分表模板有 32 个子项（细分到每个二级指标），用户手上可能有简化版（9 行 = 5 个构面 + 4 个服务/定量项）。填写评分表前先确认用户模板的实际行数。如果需要以简化版为准（每个构面一行总分），直接提供各构面的最终分数即可。

20. **核心池 1- 文件不是立即生成的** — 条件 01（现场尽调记录）在初次材料准备阶段没有对应文件。不要自行编造或从其他管理人复制。1- 目录保持空白，等用户安排现场尽调后补充。
21. **基础池证据编号从旧池文件重新映射** — 从已有池目录（如 jul-06-duohemei/）复制证据到基础池时，编号策略不同：旧池文件的子编号（1-1、1-2、5-3）在基础池中重新映射为扁平编号（1、2、3），与基础池条件的实际编号对应。不要直接把旧文件名搬过来，等用户指定每个条件编号后再命名。
22. **评分表只改 M/N 列，不动其他列**
21. **评分表只改 M/N 列，不动其他列** — 填写评分表时，只能修改 M 列（评价人意见）和 N 列（评价人打分）。**不要把策略类型描述文字（如"以股票为主要投资标的的私募基金"）、权重比例、一级指标等填入评分表的其他列**。模板的合并单元格结构已经定义了这些字段，额外写入会破坏格式，被 boss 判定为"加入了很多莫名其妙的东西"。特别地：
    - 不要往 C 列写策略类型描述（这是权重比例列）
    - 不要往 B 列已经合并的"公司生存发展能力"等字段重新写入
    - 不要往 E 列已经合并的"业内认同度"等一级指标写入
    - 所有数据只填 M（评价人意见，列 13）和 N（评价人打分，列 14）
    
22. **复制 .xlsx 模板比创建 .xls 更安全** — 评分表模板有 33 个合并单元格和复杂的公式结构。直接复制辰元或其他管理人的 .xlsx 模板后用 openpyxl 仅修改 M/N 列，比用 xlrd/xlwt 创建新 .xls 文件更可靠。如果尝试用 openpyxl 从零创建评分表，容易触发 `'MergedCell' object attribute 'value' is read-only` 错误。**规则：始终复制已有 .xlsx 模板，只改数据列，不重建结构。**

23. **交叉池复制时，用户一次给一个文件** — 从旧池（如 `jul-06-duohemei/`）复制文件到新池（如 `jul-09-duohemei-basic-pool/`）时，用户每次只给一个源文件名 + 目标文件名。**不要批量猜测下一个文件或编号**。等用户给出下一对映射再处理。用户会说"只需要基础池"来纠正错误的双向复制。

24. **外部信用核查用 Computer Use 打开本地 Safari** — 当云浏览器无法处理实名认证/验证码时，用 Computer Use MCP（`open-computer-use`）打开 macOS 本地 Safari。流程：`get_app_state('Safari')` → 点击目标标签页或地址栏 → 输入 URL → Return 导航。注意焦点可能跳回之前的标签页，需要重新点击目标标签页再输入。告诉用户页面已打开让他们亲自搜索。Wind 3.1M 是桌面终端功能，非网页。

25. **解压后先验文件再删原始包** — 解压 .rar/.zip 后，**先确认文件存在（ls 或检查文件数），再删原始压缩包**。顺序不可逆。用户重发压缩包时意味着要重新处理，不是删掉完事。记忆已存规则：解压→验文件→删原包。
